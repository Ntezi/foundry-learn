# 08 — Common Pitfalls in Use Case Scoping

*Module: Use Case Preparation Steps · Inspected September 23, 2026 · Notes: Ready for Review*

## Six pitfalls

1. **Technical scoping before business scoping.** Technical scoping should come **second, as late as possible**, so it doesn't steer the use case too early. Start without technical constraints to understand the whole problem space, then slice it if needed.
2. **Rebuilding the existing workflow as-is in Foundry.** Question the use case's bounds: what comes before the start, and after the end? Question the user flow. **Ignore the existing solution as much as you can**; it will still be there for technical scoping. Focus on the **operational** problem, not the technical one.
3. **Expecting technology alone to solve it.** The **business must be at the center from day one** and throughout iteration. Secure users' time for fast iterations and involve them as **solution designers**.
4. **Skipping desk-sides and walkthroughs.** They are a **requirement**. Watch how users work: what tools, what tasks, who they talk to, what they produce. Step back and think end to end.
5. **Aiming for the perfect solution up front.** Scoping is about understanding the problem, the value of solving it, and a **first view of the end-to-end solution**. **Start building fast and iterate.**
6. **Scoping for months.** Don't try to capture everything. The output shouldn't be a perfect mock-up, IT diagram or long list of user stories (it can include some of these). Otherwise you end up planning a multi-month or multi-year delivery instead of rapid, iterative development.

**Remember:** business before tech; don't copy the old workflow; users as co-designers; desk-sides are mandatory; build fast and iterate.

**Review question:** a team plans to copy their spreadsheet process into Foundry screen by screen. Which pitfall is that, and what should they do? Reproducing the existing workflow as-is. Question the bounds and user flow, and focus on the operational problem.
