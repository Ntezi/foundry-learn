# Glossary

One line per term, with the official page it comes from and the note that explains it. **All definitions are [Docs] paraphrases.**

Seeded on October 23, 2026 from the Observability overview, Data Health and monitoring-views core-concepts pages; terms are added as each module's notes are written (66 terms, modules 00–03 written, October 23, 2026). Automate terms are in the [Apps glossary](../Apps/GLOSSARY.md); audit-log terms in the [Security glossary](../Security/GLOSSARY.md); indexing and Funnel terms in the [Ontology glossary](../Ontology/GLOSSARY.md).

|---|---|---|---|
| **24-hour own-execution access** | Users always see logs for their own executions from the past 24 hours with only view-execution-history, independent of log access settings, except on CBAC stacks | [page](https://www.palantir.com/docs/foundry/aip-observability/log-permissioning/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Alert** | A notification with a low, medium or high severity sent to subscribers when a rule triggers | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Alert debug page** | The diagnostic view for one monitor rule firing on one resource: current value and threshold, status badge, SOP links, metric chart, 30-day alert history and links into Workflow Lineage, Ontology Manager and Code Repositories; functions and actions with single-condition rules only | [page](https://www.palantir.com/docs/foundry/monitoring-views/alert-debug-page/) | [01-03](01-monitoring-views/03-alerts-the-debug-page-and-external-systems.md) |
| **Attributed project** | The project a resource first emitted telemetry under; log access must also be enabled there if the resource has since moved | [page](https://www.palantir.com/docs/foundry/aip-observability/log-permissioning/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Automatic check schedule** | A time-based check evaluated when the dataset updates and when the configured threshold elapses; each update resets the timer to now plus the threshold | [page](https://www.palantir.com/docs/foundry/health-checks/check-evaluation/) | [02-02](02-health-checks/02-schedules-watching-and-notifications.md) |
| **Build status check** | Whether the dataset’s most recent build succeeded, across the whole process to the final dataset; intermediate datasets’ own build status checks are not updated | [page](https://www.palantir.com/docs/foundry/health-checks/checks-reference/) | [02-03](02-health-checks/03-checks-reference.md) |
| **Caller** | In run history, the resource that triggered an execution: a Workshop application, agent, third-party application, automation, action or other system component | [page](https://www.palantir.com/docs/foundry/aip-observability/run-history/) | [03-01](03-ontology-and-aip-observability/01-overview-and-run-history.md) |
| **Check group (sunset)** | The predecessor of monitoring views: a subscription to a set of health checks with an aggregated email digest; it never ran checks; no new groups can be created and existing ones should be upgraded | [page](https://www.palantir.com/docs/foundry/monitoring-views/check-groups/) | [01-04](01-monitoring-views/04-monitoring-faq-and-the-check-groups-sunset.md) |
| **Composite monitoring rule** | A rule with several conditions joined by AND; it triggers only when every condition reaches a configured severity, at the lowest severity they all reach | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Data expectations** | Checks defined in a Code Repository that run during the build, can abort it on error, and report into Data Health; packaged automatically with a transformation in a Marketplace product | [page](https://www.palantir.com/docs/foundry/health-checks/check-types/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Data freshness check** | A freshness check on the data: time between the last committed transaction and the maximum of a timestamp column; runs only when a transaction commits | [page](https://www.palantir.com/docs/foundry/health-checks/check-types/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Data Health** | The Foundry application for monitoring the health of platform resources; it has two feature sets, monitoring views and health checks, and alerts through notifications, email digests, PagerDuty, Slack or webhooks | [page](https://www.palantir.com/docs/foundry/observability/data-health/) | [00-01](00-orientation/01-the-observability-map.md) |
| **Dataset partition check** | Passes with fewer than 50 files, or when at least 90% of 50 or more files exceed 96MB; no options | [page](https://www.palantir.com/docs/foundry/health-checks/checks-reference/) | [02-03](02-health-checks/03-checks-reference.md) |
| **Escalate (status checks)** | The option on schedule, build, job and sync status checks to raise severity after consecutive failures | [page](https://www.palantir.com/docs/foundry/health-checks/checks-reference/) | [02-03](02-health-checks/03-checks-reference.md) |
| **Evaluation window** | For live-deployment rules, the period throughout which a condition must hold before the rule alerts; a brief excursion that recovers does not trigger it | [page](https://www.palantir.com/docs/foundry/monitoring-views/rules-reference/) | [01-02](01-monitoring-views/02-monitoring-rules-reference.md) |
| **Exportable markings (Slack source)** | The markings and organizations a Slack source may export; a monitoring alert shows a resource’s name in Slack only when every marking on it is in that list, otherwise its RID | [page](https://www.palantir.com/docs/foundry/monitoring-views/external-systems/) | [01-03](01-monitoring-views/03-alerts-the-debug-page-and-external-systems.md) |
| **Failure rate (colour mode)** | A Workflow Lineage colour legend under Health that colours action types, functions and AIP Logic functions by the share of runs that failed over a window of at most one day; automations show as No runs | [page](https://www.palantir.com/docs/foundry/aip-observability/metrics/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **Foundry Telemetry Service (FTS)** | The service whose data feeds the near real-time success/failure counts and P95 duration | [page](https://www.palantir.com/docs/foundry/aip-observability/metrics/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **foundry-telemetry-service operations** | read-metrics (in Viewer) for metrics; view-execution-history (in Editor) for run history and logs; both grantable through custom roles | [page](https://www.palantir.com/docs/foundry/aip-observability/log-permissioning/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **foundryTraceId / x-b3-traceid** | The Foundry-assigned identifier used to fetch telemetry, and the standard distributed-tracing identifier carried best-effort in the tags of each service log entry | [page](https://www.palantir.com/docs/foundry/aip-observability/trace-view/) | [03-02](03-ontology-and-aip-observability/02-trace-views-service-logs-and-debugging.md) |
| **Global log search** | Log search across a Workflow Lineage graph on cloud enrollments: a selected function, action, chatbot, deployment or model is searched as the log-producing resource, an automation as the source executor; scope across selected resources or within the selected call chain | [page](https://www.palantir.com/docs/foundry/aip-observability/log-search/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Health check** | A detailed check configured on one dataset, schedule or table, covering status, time, size, content and schema; alerts through in-platform notifications and email | [page](https://www.palantir.com/docs/foundry/health-checks/overview/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Health tab** | Where a dataset’s or table’s checks are added, edited and their history viewed (Dataset Preview); for a schedule, Data Lineage’s Metrics > Health | [page](https://www.palantir.com/docs/foundry/health-checks/overview/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Job (health checks)** | A Spark computation defined by one transform, producing one dataset (or several from a multi-output transform), broken into stages | [page](https://www.palantir.com/docs/foundry/health-checks/check-types/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Job status check** | Triggered whenever its dataset is refreshed or created by any build; passes if the target dataset builds even when the build fails downstream; not evaluated when the build fails upstream (the dataset registers a cancelled build) | [page](https://www.palantir.com/docs/foundry/health-checks/check-types/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |
| **Log access** | The administrator setting, on a project (and attributed project) or as a resource-level override, that lets users with Edit on the source executor read trace and service logs for executions they did not run, under the markings applied at enablement | [page](https://www.palantir.com/docs/foundry/aip-observability/log-permissioning/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Log access overview** | The dialog, from a node or the Run history and Log search panels, listing the three requirements (role, log access policy, markings) and whether the viewer meets each | [page](https://www.palantir.com/docs/foundry/aip-observability/log-permissioning/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Log export** | A stream, where the enrollment has it, containing all telemetry (logs, metrics, traces) for an organization, for analysis in Foundry or export to third-party systems | [page](https://www.palantir.com/docs/foundry/observability/overview/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **Manual check schedule** | A check evaluated at a regular interval (by minute, hourly, daily, weekly or custom) regardless of when the dataset builds | [page](https://www.palantir.com/docs/foundry/health-checks/check-evaluation/) | [02-02](02-health-checks/02-schedules-watching-and-notifications.md) |
| **Median deviation** | A check parameter expressing a threshold as approximate standard deviations from the median of recent builds, computed from the median absolute deviation (σ = MAD × 1.4826) | [page](https://www.palantir.com/docs/foundry/health-checks/checks-reference/) | [02-03](02-health-checks/03-checks-reference.md) |
| **Metric (monitoring)** | What a resource emits (metrics or logs); monitors are built on top of metrics to set a standard of performance for a resource | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Monitoring rule** | A threshold or set of thresholds on the metrics of a resource type within a scope, with tolerances and a severity | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Monitoring status (colour mode)** | A Workflow Lineage colour legend under Health that colours each node by the highest severity among its firing monitors, with No monitors configured marking coverage gaps | [page](https://www.palantir.com/docs/foundry/monitoring-views/overview/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Monitoring view** | A collection of monitoring rules that a group of subscribers care about; monitors resources at scale through scope-based rules | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Observability Chart widget** | The Workshop widget that plots one resource’s metrics (execution counts, P95 duration, CPU, memory) over time | [page](https://www.palantir.com/docs/foundry/observability/dashboards/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **Observability dashboard** | A Workshop module composed of Observability Chart widgets plotting resources’ metrics over a shared time range | [page](https://www.palantir.com/docs/foundry/observability/dashboards/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **P95 duration** | The execution-duration metric reported for functions, actions and AIP Logic over the last 30 days, alongside success and failure counts | [page](https://www.palantir.com/docs/foundry/observability/overview/) | [03-04](03-ontology-and-aip-observability/04-metrics-performance-and-observability-dashboards.md) |
| **Pausing a check** | Temporarily snoozing a check’s alerts for all watchers and subscribers; deleting removes its configuration and schedule | [page](https://www.palantir.com/docs/foundry/health-checks/watching-checks/) | [02-02](02-health-checks/02-schedules-watching-and-notifications.md) |
| **Primary key check** | Checks that a column’s values are 100% unique and non-null; the approximate unique percentage check is not suitable for this | [page](https://www.palantir.com/docs/foundry/health-checks/checks-reference/) | [02-03](02-health-checks/03-checks-reference.md) |
| **Producing resource** | The resource in a call chain that emitted a log entry, as opposed to the source executor that started the chain | [page](https://www.palantir.com/docs/foundry/aip-observability/log-search/) | [03-03](03-ontology-and-aip-observability/03-log-search-and-log-permissions.md) |
| **Resource (monitoring)** | A thing in Foundry that can be monitored: datasets, agents, schedules, objects, link types, live deployments and more | [page](https://www.palantir.com/docs/foundry/monitoring-views/core-concepts/) | [01-01](01-monitoring-views/01-monitoring-views-and-core-concepts.md) |
| **Run history** | The tab on a function, action, automation or AIP Logic resource in Workflow Lineage listing its executions over the past 30 days | [page](https://www.palantir.com/docs/foundry/aip-observability/overview/) | [03-01](03-ontology-and-aip-observability/01-overview-and-run-history.md) |
| **Run history filters** | Status, timestamp range, user, run time range, version (functions only), caller and failure type, combined with AND | [page](https://www.palantir.com/docs/foundry/aip-observability/run-history/) | [03-01](03-ontology-and-aip-observability/01-overview-and-run-history.md) |
| **Salted join** | The FAQ’s fix for a skewed join: a random salt column on the large side, the small side exploded N times, joined on key and salt; makes the build likelier to succeed, not faster | [page](https://www.palantir.com/docs/foundry/health-checks/builds-checks-faq/) | [02-04](02-health-checks/04-builds-and-checks-faq-health-checks-in-a-marketplace-product.md) |
| **Scaling deficit** | Ideal replica count minus target replica count for a live deployment; positive means under-provisioned, negative over-provisioned | [page](https://www.palantir.com/docs/foundry/monitoring-views/rules-reference/) | [01-02](01-monitoring-views/02-monitoring-rules-reference.md) |
| **Schedule (health checks)** | A collection of jobs with defined target datasets configured to run on a recurring basis; can represent a subset of a pipeline that builds together | [page](https://www.palantir.com/docs/foundry/health-checks/check-types/) | [02-01](02-health-checks/01-health-checks-and-the-types-of-checks.md) |

| **Service logs** | The chronological log entries of one execution at INFO, WARN, ERROR, DEBUG and TRACE, including console.log and logging statements from functions and models | [page](https://www.palantir.com/docs/foundry/aip-observability/service-logs-and-debugging/) | [03-02](03-ontology-and-aip-observability/02-trace-views-service-logs-and-debugging.md) |
