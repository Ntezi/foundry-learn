# 05 — Models in the Ontology and model functions

*Sources: [Models in the Ontology](https://www.palantir.com/docs/foundry/manage-models/models-in-the-ontology/) · [Model adapters in the Ontology](https://www.palantir.com/docs/foundry/integrate-models/model-asset-osdk/) · [Functions on models](https://www.palantir.com/docs/foundry/model-integration/functions-on-models/) · [Model functions](https://www.palantir.com/docs/foundry/model-integration/model-functions-guide/) · checked October 23, 2026 · Ready for Review*

The seam with the Ontology area. [Ontology 09-04](../../Ontology/09-functions/04-functions-on-models-and-llms.md) showed the *function* side: how code imports and calls a model function. These four pages are the *model* side: what a model function is, how its versions follow the model's, what happens when the API changes, how row-wise publishing flattens the signature, and how an adapter can take Ontology objects directly instead of columns.

## Why models go into the Ontology

**[Docs]** "it is often useful to run model inference in the context of Ontology objects, binding object properties to model inputs, and interpreting the result through the lens of the Ontology": a model-backed Action, or Workshop elements "directly to model output". The mechanism is "Functions on objects with the ability to call into Modeling Objective live deployments or model direct deployments". **[Explanation]** So *models in the Ontology* is not a storage feature; the Ontology never holds the model. It holds properties the model's batch output backs ([Ontology 15-03](../../Ontology/15-advanced-patterns/03-models-in-the-ontology.md)) and functions that call the model live.

## Model functions

**[Docs]** "Model functions are automatically generated functions that wrap live model deployments", with "the same input and output API as the underlying model", callable "from TypeScript, Python, or used directly in applications". Publish from either kind of deployment: a direct deployment ("You can only have one function per branch"), or an objective live deployment's *Publish Function* card, which "will be guided through the process of setting parameters for the function". "Both methods produce functionally equivalent model functions": "simple wrappers that defer all logic to the underlying live deployment, but with the model API translated to input and output types recognized by functions."

**[Docs]** The *Functions on models* page: model functions can be called from TypeScript v1, v2 and Python; "TypeScript v2 and Python repositories support only model functions that are tied to an ontology"; "Model functions created in or after February 2026 are tied to an ontology instead" of a space, and the TypeScript v1 form for those imports `Queries` from `@foundry/ontology-api`. The three code examples all call a deployment whose API input is `input_df` and read `output_df` from the result.

## Versions and API changes

**[Docs]** Two upgrade behaviours:

| Deployment | When a new model version arrives | What you do |
|---|---|---|
| **Direct** | "a new version of the associated function is also automatically created"; consumers need not change "unless the model API has changed" | Nothing, unless the API changed |
| **Objective live** | On releasing a version "with an API change", a warning appears and "The dialog will guide you through the process of publishing new function versions for any deployment affected by the release"; "You should not ignore this warning" | Publish a new function version, or "Usages of the current function version will break" |

**[Docs]** Why: "Both functions and the underlying live deployment validate inputs/outputs against the current API", so "Previous model function versions will fail validation and stop working". Upgrading the dependency: TypeScript v1 edits `resources.json` to the new function version ("This will automatically regenerate the necessary type bindings"); TypeScript v2 and Python "remove and re-import the function using the Resource import sidebar". Marketplace-installed models are the exception: "Marketplace manages function publication during installation and product upgrades", and a new version on the default branch "updates the live deployment without automatically publishing a function version". For change management, several functions on several branches of one model let a project import several model versions.

**[Explanation]** The two behaviours are the same rule seen from two sides: a *function version* mirrors a *model API*, and only an API change forces consumers to move. The objective's warning is the moment to publish; the Ontology area's rule that `liveFraudScore` maps columns by hand ([Ontology 09-04](../../Ontology/09-functions/04-functions-on-models-and-llms.md)) is exactly the code that breaks if the warning is ignored.

## Row-wise publishing

**[Docs]** "Row-wise publishing flattens the function API for models with a single tabular input and a single tabular output, allowing each function call to process a single row instead of an array." It is "enabled by default" for such models; an API with "any additional input or output, such as one tabular input alongside a Parameter input, is not eligible", and the function "accepts and returns arrays instead". The page's housing example: with row-wise processing the function takes `area_code`, `num_bedrooms`, `num_bathrooms` and returns those plus `predicted_price`; without it, `input_df: Array<{...}>` in and `output_df: Array<{...}>` out. Toggle *Enable row-wise processing* when publishing a new function version. The alternative the page offers: "consider using an Object or ObjectSet directly in the Model API".

**[Explanation]** Row-wise is convenient for one object on screen and wrong for a column over many rows, where one array call beats many row calls ([Ontology 09-04](../../Ontology/09-functions/04-functions-on-models-and-llms.md) said the same from the function side). The fraud adapter's one-in, one-out API keeps both options open; adding a `Parameter` input (a threshold, say) would silently lose row-wise eligibility.

## Objects and object sets in the adapter

**[Docs]** With an `ontology_sdk` package generated from Developer Console or Code Workspaces, an adapter declares `pm.Object(Employee)` and `pm.ObjectSet(EmployeeObjectSet)` as inputs and, say, a `pm.Parameter(type=str)` output; test inputs can be picked from the Ontology on the model's query page while a direct deployment runs; the function can be published with object inputs. Inside `predict()` or `transform()`, `FoundryClient()` can "query functions, objects, and LLMs", for instance `client.ontology.objects.Employee.get(pk).first_name`; the page frames this as "pro-code LLM based workflows where you can interact with the Ontology and utilize traditional modeling techniques".

**[Explanation]** This removes the hand mapping [Ontology 09-04](../../Ontology/09-functions/04-functions-on-models-and-llms.md) called "where bugs live": the function passes the object, the adapter reads the properties it needs by name, and a renamed property fails in the adapter's own code, where the SDK types catch it, rather than quietly in a wrapper. The cost is a dependency from the adapter on one Ontology's SDK, so the model is now bound to that Ontology; the external-model page's reason for not wrapping general-purpose models ([03-03](../03-bringing-models-in/03-externally-hosted-models.md#when-not-to-wrap)) is the same coin, other side. Also, the page tests object inputs on a *direct* deployment's query page; how an objective live deployment's *Query* tab handles them is not stated, so a model that will be served through an objective should keep a column API or verify first.

## For Kestrel

**[Example]** *Proposed*, closing the question left in [01-02](../01-models-and-model-adapters/02-writing-a-model-adapter.md#for-kestrel): both adapters **keep column APIs**, one tabular in and one out, for three reasons from these pages: it keeps row-wise publishing available for the one-shipment and one-payment calls while the array form stays available for columns; it avoids binding the model to an Ontology SDK version that Daniel's repositories would then have to track; and the objects-in-API path is documented against direct deployments, which Kestrel does not use ([03](03-deployments-live-batch-direct-and-branching.md#for-kestrel)). `pm.Object(Shipment)` is *considered, not adopted*, to be revisited if the hand mapping in `deliveryRisk` and `liveFraudScore` causes a second production bug. Both functions are published from the objectives' production live deployments, ontology-bound (they are new, so February 2026 applies), with **row-wise processing on**, since each is called for the object on screen; Workshop columns over many rows use the batch property, never the function ([Ontology 15-03](../../Ontology/15-advanced-patterns/03-models-in-the-ontology.md)). The release checklist of each objective ([02](02-checks-on-submissions-and-objective-settings.md#for-kestrel)) gets one line: *if the release dialog warns of an API change, publish the new function version and re-import it in the Delivery Desk and Kestrel Pay repositories before Mark as production*. One more `modelVersion` detail: because the adapter stamps the identifier into `df_out` ([01](01-the-objective-lifecycle.md#for-kestrel)), the function's return type carries it, and *Record fraud score* stores it with no extra lookup.
