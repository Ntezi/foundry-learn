# 02 — The evaluation dashboard, metric views and MetricSets

*Sources: [Review model metrics in the evaluation dashboard](https://www.palantir.com/docs/foundry/evaluate-models/review-model-metrics/) · [Custom modeling objective metric views](https://www.palantir.com/docs/foundry/evaluate-models/customize-metric-views/) · [MetricSets reference](https://www.palantir.com/docs/foundry/evaluate-models/metric-sets-reference/) · checked October 23, 2026 · Ready for Review*

Where the metrics of [01](01-automatic-and-in-code-evaluation.md) are read: the objective's evaluation dashboard, its tabs, and the pinned views an objective owner curates for every submission. The third page is the `MetricSet` reference, read for what the dashboard still accepts from code and for its own deprecation notice.

## The evaluation dashboard

**[Docs]** "The evaluation dashboard provides a standard and centralized place for model metric and performance evaluation." By default "only metrics that have been generated by the evaluation dashboard configuration are displayed" (the setting of [05-02](../05-modeling-objectives-and-deployments/02-checks-on-submissions-and-objective-settings.md#settings)); metrics "are shown based on the intersection of the selected evaluation dataset and model submissions".

**[Docs]** Two selectors. The **evaluation dataset**, or "a specific dataset transaction of an evaluation dataset": without a transaction "you will see the most recent metrics results for every selected model submission"; with one, only metrics built on it. "It is most statistically accurate to compare models across a specific transaction", while cross-transaction comparison helps "where the model schema has changed". The **models**: the union of *Select models* (chosen one by one) and *Search for models*, which matches "metrics criteria on all data" (*Overall*) or on a subset, an owner or submitter, or metadata.

**[Docs]** Layout: tabs, "a combination of the subsets configured in the evaluation configuration" and, if enabled in the settings, "the custom pinned metrics views".

**[Explanation]** The transaction selector is the dashboard's honesty switch. Two submissions compared on *latest* may have been scored on different months of data; pin the transaction and the comparison is like for like. The search-by-metric is how a large objective is pruned: *every submission with recall above 0.8 on the north-east subset* is a query, not a scroll.

## Custom metric views

**[Docs]** On a submission's page, *Actions → Pin metrics to objective* enters an edit mode where tabs are created (*+ Create new tab*) and "statistics, charts, or images" pinned; "Information configured on one submission's view, such as custom tabs created or metrics pinned, will also appear as configured for every other submission", because "Configuration is done on the modeling objective level". Interactive bar charts can be built from the metric explorer and pinned. The tabs show on the dashboard only when *Show pinned tabs in evaluation dashboard* is on. Patterns the page names: "Key Metrics/Theories", "Sensitive Features", and "Outlier Information". The configuration "should evolve as new data comes in, new feedback is received, and new theories are tested".

**[Explanation]** A pinned tab is a reviewer's reading order, fixed once for every candidate. The *Sensitive Features* pattern is the one that pairs with subsets: configure the subset in [01](01-automatic-and-in-code-evaluation.md), pin its recall and confusion matrix here, and the fairness check of [05-02](../05-modeling-objectives-and-deployments/02-checks-on-submissions-and-objective-settings.md#for-kestrel) becomes a tab a reviewer opens, not a query a reviewer must know to run.

## `MetricSet`s

**[Docs]** The page's heading says *Planned deprecation*, and the notice repeats [01](01-automatic-and-in-code-evaluation.md#evaluating-in-code-the-deprecated-path): built for `foundry_ml`, "formally deprecated since October 31, 2025"; "For new implementations, we recommend using experiments instead"; "it is still possible to write metric sets against a model and view the metrics in Modeling Objectives". In Code Repositories they "exist only for backward compatibility with models that were initially built as dataset-backed models".

**[Docs]** What one is: "a container for named metrics which we define as any summarization of a model's output", added with `MetricSet.add(name, value, subset, stage)`. Value types: numbers (`int`, `float`, NumPy widths), a Matplotlib figure or any object with `get_figure`, `save` or `savefig` (Seaborn plots), and `foundry_ml_metrics.charts.line(...)` or `.bar(...)`, whose data "is saved" for "superior model comparison ability". The **input dataset** "is an explicit reference to the specific version of data that the model was applied to", passed as a transform input, so that "you create a record and full provenance of a model's performance". Subsets are string dictionaries (`{'sepal_length': 'long'}`; `{}` is overall). With `palantir_models`, the model is identified by the UUID part of `model_input.model_version_rid` (available from **0.1602.0**), and the metric set's dataset is then registered as an evaluation dataset in the objective's configuration.

**[Docs]** "Metric sets are represented as datasets, and are computed via Foundry Builds", so a changed model or data version means rebuilding them, or "you will not see metrics within the Model Preview".

**[Explanation]** The concept page of [00-01](../00-orientation/01-the-modelling-map.md) still calls the MetricSet the unit of an evaluation, and the glossary keeps the term for that reason. The practical rule from these three pages: evaluation of a *version* goes through experiments and evaluations ([04](../04-experiments-and-evaluations/README.md)); evaluation of a *submission* goes through the objective's configuration; `MetricSet`s are read, not written.

## For Kestrel

**[Example]** *Proposed* pinned tabs, the same on both objectives so a reviewer who learns one knows the other: **Key metrics** (recall and precision at the operating threshold, `roc_auc`, the confusion matrix, the probability distribution); **By segment** (recall per `region` for `Delivery delay`, per `cardCountry` for `Payment fraud`, as bar charts from the subset metrics); **Key cases** (the `delivery_key_cases` and `payments_confirmed_fraud` datasets' metrics, where a miss on a known case is the headline). *Show pinned tabs in evaluation dashboard* on; reviewers compare on a pinned **transaction** of the hold-out month, which the release note records, so a release can be re-read against the exact data it was judged on. No `MetricSet`s are written; the Model Studio baseline of [02-01](../02-training-models-in-foundry/01-model-studio.md#for-kestrel) is evaluated through the objective's configuration like every other submission, which is also the one place its experiment's metrics and the hand-written adapter's metrics can be read side by side.
