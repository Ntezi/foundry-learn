# 26 — Introduction — Configuring the Ontology

## Give application builders a usable model

The first half produced three datasets. They describe passages, extracted names and associations, but the later application should not have to reconstruct their meaning through joins every time. This module exposes them through Chunk and Entity object types and a relationship in the Ontology.

Open Ontology Manager when performing the practical walkthrough. The immediate purpose is to define the semantic interface that Vertex, Logic and Workshop will consume. You are moving from a pipeline's output representation to an application-facing model.

## Translate the distinction into software terms

A dataset resembles a table produced by a data job. An object type resembles a domain type with identity, properties and configured relationships. An object is a particular instance of that type. The mapping connects backing rows to those instances.

This analogy is useful, but do not assume the Ontology is just a class declaration in your application code. It is a shared platform resource with its own configuration, indexing and access context. Saving a definition and having queryable objects are different stages.

For a Chunk, the important identity is chunkId, not the summary shown to the user. For an Entity, the tutorial uses entityName as identity. Those choices inherit the strengths and limitations of the first-half key design.

## What semantic modeling does not repair

Creating an Entity object type does not resolve aliases that the pipeline left unresolved. A Chunk title generated by an LLM can still be misleading. A configured relationship can faithfully expose an incorrect pair from Join Table.

The semantic layer makes information easier to reuse; it does not automatically certify its truth. Continue carrying source provenance and interpretation limits into the application rather than treating an object as a verified fact merely because it has a type.

## Why relationships belong here

A Chunk-to-Entity link allows consumers to traverse the modeled association without rebuilding the join manually. Vertex can search around from chunks to entities; other consumers can use the same relationship. That reuse reduces duplicated integration logic.

It also makes contract changes consequential. If you change the key policy or backing datasource, existing consumers may see different objects or missing links. Treat such changes with the same care you would give a shared API or database relationship.

**Checkpoint:** explain the difference between a Chunks dataset, a Chunk object type and one Chunk object. Then explain why a successful pipeline build is necessary groundwork but not proof that the Ontology objects are available yet.
